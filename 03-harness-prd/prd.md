## Problem & user

RocketShip PMs need this handled: You are a front-end prototyper building a rough, low-fidelity prototype of "Juno PM," an AI Associate PM embedded in Slack and ProductBoard. Juno does this inside limits a human set on purpose, and defends every call it makes.

## 01 Context · Data Requirements

**Required sources, and exclusions**

One signal at a time: the text, plus its source (Slack channel/thread or ProductBoard item), author, and date.

ProductBoard item:	Edits, new linked notes-   Same as Slack: read at processing time, re-check while unresolved

## 02 Tools · System Capabilities

**The verb list**

Read a signal from Slack or ProductBoard
Frame a problem or JTBD	
Assign a tier and 0 to 4 input scores	
Propose a category label (new or existing)
Write one card to storage
Show a “Route to PM / DRI” label

**Deliberate omissions**

1. No write or reply access to Slack and ProductBoard
What’s omitted: posting, replying, editing, or deleting anything in the source systems.
Why: The skill file says Juno never acts autonomously and never auto-drafts communications. Read-only access makes that rule structural. A model told “don’t reply” can still be talked into it, but a model without a reply tool can’t. It also protects the sources themselves: the signals are the evidence, and a tool that can edit them can quietly destroy it.
2. No automatic tier conflict resolution
What’s omitted: a “higher tier wins” or “best guess” rule.
Why: Tier conflicts are the cases where the strategy doc’s own definitions overlap, so any rule the model applies is a judgment about company priorities. That belongs to the PM. Defaulting to the higher tier would also inflate P0, which is meant to mean “non-negotiable,” and a P0 label loses its force if it becomes the safe default.
3. No category merge, rename, or taxonomy tool
What’s omitted: the ability to restructure labels on its own.
Why: You said the categories are unknown and will form from inputs. A taxonomy shaped silently by the model would reflect its wording preferences, not your team’s mental model, and every later card would inherit that bias.
4. No web search or external data
What’s omitted: looking up anything outside the signal, the thread, and the strategy doc.
Why: Your scoping is internal needs only, and search would pull in exactly the external signal the scope excludes. It also invites the model to fill gaps with plausible outside facts, which breaks “do not make up anything.”
5. No requirement-writing tool in the card path
What’s omitted: generating requirements as part of creating a card.
Why: The Role mentions writing requirements from the highest needs, but producing a card and writing a requirement are different jobs with different trust levels. A card is a cheap, reviewable summary of one signal. A requirement commits the team to something. Keeping them separate means a weak card can’t flow straight into a requirement.

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

One pass per signal, plus one self-check retry. Frame, tier, score, label, then run the verification checks (section 6). If a check fails, it gets one revision. If it still fails, the card goes to NEEDS CLARIFICATION with the failure reason. It never loops until it passes.
No chaining. It doesn’t pull in more signals to “firm up” a weak one. Missing information goes in Unknowns.
Batch runs (multiple signals) process each signal independently. A failure on one doesn’t stop the others.

**Latency and cost target**

- Volume assumption: fewer than 10 signals per day.
- Processing: per signal, as it arrives. No batching.
- Latency: card within a few minutes of arrival; under ~30s
  processing including the one self-check retry.
- Cost ceiling: 2 model passes per card, max 20 per day.
- No daily budget cap.
- Thread read: bounded length; truncation shown in Unknowns.
- Track: seconds per card, passes per card, cost per accepted
  card.
- Revisit if volume exceeds ~10x current estimate.

## 06 Verification · AI Testing & Measurement

**The check before output ships**

Self-checks before storing (automatic)
Every claim is quoted. Each scored input and the tier have a verbatim supporting phrase from the signal. No quote, no score.
Nothing invented. Every field not stated appears in Unknowns as “not stated.”
Tier rules applied in order. P0 checked first, exclusions honored, P3 not assigned if the signal touches correctness, security, compliance, or onboarding.
Scope gate. Anything not “Internal (stated)” skipped framing, tier, and weight.
Format. All fields present, in order, under one page.
No drafted messages appear anywhere in the card.

**Failure behaviour**

Failure behavior
- Principle: visible gap, never a silent default or guess.
- Source unreadable: 1 retry, then log "not processed:
  source unreachable"; surface in queue.
- Thread unreadable: process signal alone; "thread not read"
  in Unknowns; NEEDS CLARIFICATION if ambiguous.
- Strategy doc unreadable: no tiering; "Tier not determinable:
  strategy doc unavailable".
- Category list unreadable: provisional label tagged
  "new, list unavailable".
- Storage unreadable: hold in session; show "unsaved".
- Self-check fail: 1 revision, then NEEDS CLARIFICATION naming
  the failed check.
- Malformed output: 1 retry, then log raw output.
- Never: guess, loop past 1 retry, drop a signal unlogged,
  message anyone, or overwrite a reviewed card.
- Queue header shows last-signal-processed time per source.
- Failure log kept; Re-run action is idempotent by source ID.
